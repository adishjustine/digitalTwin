# Wokwi ESP32: the physical layer

The ESP32 plays the **building's physical side**: a DHT22 gives the outdoor
temperature and humidity, three potentiometers set the occupancy of each zone,
and an on-board thermal model computes each zone's indoor temperature from the
weather, people, equipment, lighting and the HVAC mode your Python digital twin
commands. LEDs show what the twin decided.

```
Wokwi ESP32 --telemetry--> public MQTT broker --> Python bridge --> digital twin --> optimiser
     ^                                                                                  |
     +------------------------------ command (HVAC + lighting) <------------------------+
```

Wokwi runs in your browser and cannot reach `localhost`, so both sides connect
to a public MQTT broker (`broker.hivemq.com`). Anything you publish there is
visible to others: use a unique site id and only simulated data.

## Setup (about 10 minutes)

1. Go to <https://wokwi.com>, start a new **ESP32** project (Arduino).
2. Replace the project's files with the ones in this folder:
   `sketch.ino`, `diagram.json`, `libraries.txt`.
3. In `sketch.ino` change `SITE_ID` to something unique, e.g. `adish-dt-4821`.
4. On your PC, in the project folder:
   ```bash
   pip install -r requirements.txt
   python -m integration.mqtt_bridge --site-id adish-dt-4821
   ```
5. In a second terminal: `streamlit run app.py`, then open the
   **Live hardware (Wokwi)** tab.
6. Press **Play** in Wokwi. The serial monitor prints one line per simulated
   minute, the LEDs react, and the dashboard fills in.

## How to drive the demo

| Do this in Wokwi | What to expect |
|---|---|
| Click the DHT22 and raise the temperature to ~40 °C | Heatwave: the twin pre-cools, HVAC LEDs come on earlier |
| Turn a zone's potentiometer to 0 | Zone empties: lights go off, HVAC drops to the unoccupied policy |
| Turn all potentiometers to maximum | Extra heat from people; the twin switches to HIGH when needed |
| Compare with the dashboard's Optimiser table | Which plans were rejected and why |

**Where to look:** the twin keeps indoor temperatures inside the 22-26 °C band, so the
temperature line stays fairly flat on purpose. The Live tab's second panel (HVAC power) and the
HVAC LEDs show the response. Only the DHT22 and the potentiometers drive the live view. The
Streamlit sidebar sliders affect the offline tabs only. Indoor temperature also changes slowly
(the zones have a thermal time constant of several simulated hours), so give a change a minute
or two of real time, or lower `TICK_MS` in `sketch.ino` (for example 300) to run faster.

## Pin map (generated by `make_diagram.py`)

| Function | Zone A (Office) | Zone B (Meeting) | Zone C (Lab) |
|---|---|---|---|
| Occupancy potentiometer | GPIO34 | GPIO35 | GPIO32 |
| Lighting LED (yellow) | GPIO13 | GPIO27 | GPIO23 |
| HVAC LOW LED (cyan, on for LOW and HIGH) | GPIO12 | GPIO26 | GPIO22 |
| HVAC HIGH LED (blue) | GPIO14 | GPIO25 | GPIO21 |

DHT22 data is on GPIO15. To change the layout, edit `make_diagram.py` and run
`python wokwi/make_diagram.py`, or just drag parts around in Wokwi.

## Protocol

Lockstep, one message pair per simulated minute (1 tick = 1 real second):

```
ESP32  -> dtbems/<SITE_ID>/telemetry  {"k":12,"minute":492,"t_out":31.20,"hum":55.0,"z":[{"T":24.31,"occ":8},{"T":23.90,"occ":0},{"T":25.00,"occ":3}]}
Python -> dtbems/<SITE_ID>/command    {"k":12,"z":[[1,1],[0,0],[2,1]]}   # [hvac 0=OFF 1=LOW 2=HIGH, light 0/1]
```

The ESP32 waits for the command with the same `k` before advancing, so the loop
behaves like the offline simulator. If a command is lost it keeps the previous
settings and prints a warning. Bad telemetry (out-of-range or malformed values)
is rejected by the bridge.

## Troubleshooting

**Wokwi shows temperatures but the Python app shows nothing?** Work through this in order:

1. Wokwi's serial monitor: do you see `NO COMMAND from the Python app` lines? If yes, Wokwi is
   running but nothing answers. If you see `WiFi connecting....` or `MQTT failed`, it is not
   reaching the broker at all.
2. Stop the bridge, press Play in Wokwi, then run
   `python -m integration.check_link --site-id <your-id>` for 20 seconds. It says whether
   telemetry arrives, and if you typed a different site id than the sketch uses, it names the
   id it actually saw.
3. `SITE_ID` in `sketch.ino` and `--site-id` must be identical (case-sensitive). Remember to
   save/restart the Wokwi project after editing it.
4. Start the bridge: `python -m integration.mqtt_bridge --site-id <your-id>`. It must print
   `Connected to ...` and then one `k=...` line per Wokwi tick. If it prints
   `Connected but NO telemetry yet`, go back to step 2.
5. Only then open the **Live hardware (Wokwi)** tab in the Streamlit app. It reads
   `data/live_state.json` from the project folder (the same file the bridge writes, whichever
   folder you launched each from).


- **"no command from the Python app"** in the serial monitor: the bridge is not
  running, or `SITE_ID` differs between `sketch.ino` and `--site-id`.
- **Bridge connects but nothing arrives**: the public broker may be busy. Try
  `--broker test.mosquitto.org` and set `MQTT_HOST` to the same host in the sketch.
- **Wokwi simulation is slower than real time**: normal with WiFi. Raise
  `TICK_MS` or just let it run.
- **No Wokwi / networking problems on demo day**: run the same loop without the
  browser using `python -m integration.fake_device --mqtt --scenario "Heatwave"`
  (or without `--mqtt` for a pure in-memory run). It uses the same physics and
  the same messages.
- **Check the firmware logic on your PC**: `python wokwi/host_test/check_firmware.py`
  compiles the sketch with stub headers and checks the thermal model and command
  parser against the Python code. It does not test WiFi/MQTT/DHT behaviour.

## Limits to mention when presenting

- The "sensors" are simulated: occupancy is a potentiometer, outdoor weather is a
  DHT22 you set by hand, and indoor temperature comes from the on-board model.
- The model parameters are illustrative, not a real building.
- Live mode shows the twin controlling the virtual hardware. The fair
  conventional-vs-twin energy comparison is the offline simulator.
